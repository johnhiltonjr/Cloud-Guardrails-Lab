# ADR-002: Use Federated Pipeline Identities with Least-Privilege Access

- Status: Proposed
- Date: 2026-11-23
- Author: John Hilton Jr.
- Module: 01 — Guardrails as Code
- Related controls: C-01, C-02, C-03, C-04, C-05

## Context

Harbor and Pine Insurance needs a repeatable process for reviewing
infrastructure and security configuration changes before deployment.

Module 1 introduces GitHub Actions checks for Terraform configuration
and planned resource changes.

Pipeline access to Azure creates a trust boundary. An overly privileged
identity or compromised workflow could affect multiple subscriptions.

We need to decide how workflows authenticate, which workflows receive
Azure access, and how planning and deployment permissions are separated.

## Decision Drivers

- Security: Identify insecure changes before deployment and minimize
  pipeline permissions.
- Operational impact: Introduce automation gradually, beginning with
  validation and planning.
- Maintainability: Keep workflows and security checks in version control.
- Cost and complexity: Account for staff training, workflow maintenance,
  execution costs, and identity administration.
- Lab constraints: Limit access to the isolated Azure lab hierarchy.

## Options Considered

| Option | Benefits | Drawbacks |
|---|---|---|
| A: Federated authentication with separate planning and deployment identities | Avoids stored long-lived Azure credentials; separates permissions by function | Requires careful configuration of federation, workflow trust, and Azure roles |
| B: Stored service-principal credentials | Familiar authentication approach | Requires secure storage, rotation, and management of credential exposure |
| C: Credential-free CI with manual Azure planning and deployment | Simple starting point; CI has no Azure permissions | Requires manual execution and separate capture of plan and deployment evidence |

## Decision

Use GitHub Actions to validate, plan, and deploy Module 1 Terraform changes
to Azure.

Azure authentication will use workload identity federation, without
stored client secrets.

Use separate identities for planning and deployment:
- Planning identity: Access required to read the target configuration
  and use the Terraform backend.
- Deployment identity: Permissions required to manage the initiative
  and assignment at the approved lab scope.

Credential-free checks may run on pull requests. Azure-connected jobs
will run only for trusted changes.

Deployment will require:
1. Successful formatting, validation, Checkov, and OPA/Conftest checks.
2. Review of the Terraform plan.
3. Explicit deployment approval.
4. Application of the same saved plan evaluated by the security checks.

Changes to the configuration require a new plan and validation.

### Scope

Module 1 Azure Policy initiative and assignment deployment within
`mg-guardrails-lab`.

Exact Azure roles, backend permissions, federation subjects, and
GitHub deployment protection settings must be documented and tested
before this ADR is marked Accepted.

### Identity and Permission Design

| Workflow function | Azure access |
|---|---|
| Formatting, static scanning, and local policy tests | None |
| Trusted Terraform planning | Read access to required Azure resources, plus separately defined backend access |
| Approved Terraform deployment | Only permissions needed to manage the intended objects at their required scopes |

Before accepting this ADR, document:
- Planning identity and exact role assignments.
- Deployment identity and exact role assignments.
- Terraform backend permissions.
- Allowed repository, branch, or environment federation subjects.
- Which events may run Azure-connected workflows.
- Deployment approval requirements.

## Rationale

Federated authentication avoids maintaining long-lived Azure client
secrets in GitHub.

Separate identities limit the permissions available during planning
and deployment. Trust restrictions reduce the chance that an untrusted
workflow can obtain Azure access.

Credential-free checks provide an initial implementation step while
Azure-connected planning and deployment are developed.

## Consequences

### Benefits

- Repeatable security checks before deployment.
- Reviewable workflow and configuration changes.
- Traceable validation and deployment records.
- Separation of planning and deployment permissions.
- Reduced dependence on stored Azure credentials.

### Risks and Limitations

- Incorrect federation settings could allow unintended workflow access.
- Excessive role assignments could expand the impact of compromise.
- Malicious workflow changes could misuse authorized access.
- Checks detect only the conditions covered by their rules.
- Terraform plans and state may contain sensitive information.
- Staff must maintain workflows, dependencies, permissions, and tests.

### Operational Responsibilities

- Development/platform team: Maintains workflows and Terraform execution.
- IAM team: Maintains federated identities and approved role assignments.
- Security team: Defines security checks and reviews changes to workflow
  trust, permissions, and branch protection.
- VP of Security and Infrastructure: Approves major changes to the trust
  model or deployment authority.

In the lab, John performs these roles and records the review decisions.

## Validation

| Test | Expected Result | Evidence |
|---|---|---|
| Submit a configuration violating a tested control | The relevant check fails and prevents progression through the protected workflow | Failed run and rule output |
| Submit a configuration satisfying the checks | Required checks pass; the change becomes eligible for the next approved step | Successful run |
| Attempt a write using the planning identity | Azure denies the operation | Authorization error |
| Attempt authentication from an unauthorized workflow context | Federated authentication fails | Authentication result |
| Run an approved deployment | The deployment identity changes only the intended objects within its authorized scope | Apply output and Azure activity record |

Passing CI checks does not by itself prove that deployment succeeded.

## Rollback and Review

If a workflow or identity is compromised:
- Pause the affected workflow.
- Disable the affected federated trust or remove its Azure access.
- Investigate activity and assess deployed changes.
- Restore a reviewed workflow configuration before resuming execution.

Reverting workflow code does not reverse changes already deployed to Azure.
Infrastructure rollback requires a separate reviewed plan and apply.

Review this ADR when:
- Pipeline permissions or federation subjects change.
- Deployment automation is introduced.
- Repository ownership or workflow trust changes.
- AWS is added to the implementation scope.
